# 2026-2027 第 1 学期课表导入

## 直接在 Supabase 网页导入（本次使用）

**已改为 CSV 上传 + 小 SQL。旧 `import-output` 中约 9 MB 的 SQL 太大，不再用于网页导入。** 新文件全部在 `supabase-web-import`，**不需要在本地运行 Node.js、PowerShell、psql 或数据库**。

1. 在当前项目 **SQL Editor** 运行 `supabase-web-import/00-create-upload-table.sql`，使用默认 `postgres` 数据库角色。
2. 转到 **Table Editor**，打开新建的 `public.timetable_upload_2026_2027_1`，通过 **Import data from CSV** 上传 `supabase-web-import/01-upload.csv`。
3. 在 SQL Editor 运行 `supabase-web-import/02-check-upload.sql`，必须显示 **READY**（10,064 条中转记录，含教师、课程、班级和课表）。
4. 运行 `supabase-web-import/03-dry-run.sql`，最后 ROLLBACK，不提交业务导入。无错误后再运行 `supabase-web-import/04-import.sql` 正式提交。
5. 运行 `supabase-web-import/05-verify.sql`，核对 4,602 条选课记录和 6,979 段时段。

详细步骤和上传失败后的处理见 `supabase-web-import/网页导入步骤.md`。SQL 最大约 23 KB，约 10 MB 的数据单独作为 CSV 上传。

若旧版校验显示 `NOT_READY` 但行数为 10,064，先使用已更新的 `02-check-upload.sql`。新版比较完整 JSON 内容及记录编号，允许对象字段顺序和排版空格变化；不会放过真实字段变化。若仍为 `NOT_READY`，运行只读的 `02a-diagnose-upload.sql` 定位差异类型，把结果用于进一步排查，先不要清空或重复上传。后续预演和正式导入也应重新复制当前文件的内容，以使用同一套校验。

不要把原始 `courses.csv` 直接导入现有 `courses` 表：它包含教师、班级、地点和多段时间，需要 SQL 完成拆分、关联及防重。也不要执行旧教师导入包中的清理脚本。下面的本地生成命令仅供未来修改配置或重新生成 SQL 时参考，本次不必运行。

本目录的 `courses.csv` 是数据源。执行 `node scripts/import-timetable.mjs` 会校验全部 CSV，生成可执行的 PostgreSQL SQL、只读验收查询和问题报告；**生成过程不连接数据库**。数据库是本项目使用的 Supabase PostgreSQL。请在项目根目录运行命令，Node.js 22 或更新版本。

## 数据模型

保留现有 `colleges`、`teachers`、`courses`、`terms`、`course_offerings`，新增：

- `timetable_teacher_links`：课表中的教师姓名和开课单位到现有教师 ID 的映射。`pending` 表示同名候选不止一人，暂不关联任何教师页面。
- `timetable_course_keys`：开课单位及课程代码到现有课程 ID 的映射。现有 `courses` 没有课程代码字段。
- `timetable_classes`、`timetable_classrooms`：教学班编号和教室。教学班与开课的对应关系在 `timetable_section_classes` 中，原始名称同时保留。
- `timetable_sections`：每个选课编号一条。保存学分、性质、容量和完整 CSV 原始行。
- `timetable_meetings`：一条上课时段一行，存具体教学周数组、星期、节次、教室、该时段教师、原始时间地点。`NULL` 星期/节次表示 CSV 仅给周次。
- `timetable_schedule`：查询用视图。时段教师优先于课程教师；当时段教师尚未匹配，`teacher_id` 为 `NULL`，不误指到课程教师。
- `timetable_college_updates`：记录被导入修改的教师学院及旧值。

为兼容现有教师列表、课程搜索和“本学期授课”筛选，已解析的教师和课程同时补入 `course_offerings`。这一表仍是教师、课程、学期粒度；具体教学班及时间应查 `timetable_schedule`。

## 去重与学院规则

导入时在事务中锁定教师等基础表，再按去首尾空白、合并中间空白、大小写不敏感的姓名查找当前数据库。唯一同名记录沿用其教师 ID，因此原页面、评价及评分保留。同名记录有多条时先标 `pending`，不会新建教师页或猜测匹配。数据库没有该名字时，只创建一个无初始评分的教师页面；同一个名字出现在多个开课单位时复用这一页。新教师原始所属学院未知时先挂“课表教师院系待核实”。

仅当该教师在整份课表中对应**唯一一个可映射为学院的开课单位**，才更新其学院；多个可映射学院或完全没有可映射学院时，原学院保留。更新记录见 `timetable_college_updates` 和导入时最后一个结果集。开课单位可能只是授课单位，**不是人事归属证明**；同名也不是全校唯一身份标识，仍应核对改动清单。CSV 中“附中、就业中心、武装部”等未确定学院映射的单位保留原文，不自动新建同名学院。已创建的教师页面使用课表姓名和“课表教师院系待核实”初始信息，待可确认时按规则更新。

本地 `migration-output/20260927/teachers.csv` 有 2,624 位教师，曾用于本地预演。`import-output/teacher-preview.json` 根据这份**历史快照**列出预计复用、新建和学院更新，并非线上当前状态；正式 SQL 会重新查询当前数据库。用现有教师目录实测，复用 1,458 位教师、新建 743 位，227 位已有教师的学院更新；新建教师在多开课单位但唯一学院时也会被补全学院。姓名唯一匹配可能混淆真实同名不同人，在运行前应重点审阅 `teacher-preview.json` 中的 `collegeUpdates` 和 `newTeachers`。

## 执行

Windows 可以直接使用 `scripts/Invoke-TimetableImport.ps1`。先安装或准备 PostgreSQL 客户端 `psql`，从 Supabase 的 Connect 面板取得连接参数，将 `PGHOST`、`PGPORT`、`PGDATABASE`、`PGUSER` 设置为该数据库的连接值，并按连接要求设置 `PGSSLMODE=require`。密码使用 `psql` 的交互提示或 libpq 密码配置，勿写进源码。随后在项目根目录运行：

```powershell
./scripts/Invoke-TimetableImport.ps1 -Mode DryRun
# 检查预演结果后正式提交：
./scripts/Invoke-TimetableImport.ps1 -Mode Apply
./scripts/Invoke-TimetableImport.ps1 -Mode Verify
```

下面是对应的分步说明。若不用 PowerShell 包装脚本，也可直接运行生成器和 SQL。

1. 在项目根目录执行 `node scripts/import-timetable.mjs`。需要换源、配置或输出目录时，使用 `--csv`、`--config`、`--out` 参数。每次改动 `scripts/timetable/config.json` 后都要重新生成。该配置里的 `collegeAliases` 是明确映射；`teacherOverrides` 可按 `import-output/teacher-keys.json` 中的 `key` 指定现有教师 ID，`courseOverrides` 可指定现有课程 UUID。举例：`"[\"数学\",\"王老师\"]": "legacy_teacher_123"`。映射目标不存在时整批报错回滚。
2. 阅读 `import-output/analysis-report.json` 的 `issues` 和 `unknownDepartments`、`import-output/teacher-preview.json` 的预计教师处理。预演报告当前有 421 条只有周次、5 条无上课时间、192 个重叠时段提示、5 条缺教师、1 条容量为 `-1`。这些行都保留；不推断星期、节次、容量或重叠时段的取舍。
3. 使用有 DDL 与数据写权限的数据库所有者角色（Supabase SQL Editor 默认的 `postgres`，或受信任的直连会话）执行 `import-output/00-dry-run.sql`。最后一条是 `ROLLBACK`，会输出新增计数、待核实教师、学院无法唯一判断的教师，但**不会提交任何数据**。文件约 9 MB；若 SQL Editor 拒绝大文件，应使用直连 `psql -v ON_ERROR_STOP=1 -f "schule2026-2027-1/import-output/00-dry-run.sql"`。不要使用前端 anon key 执行。
4. 检查预演结果，特别是 `pending` 教师、学院改动与新建数量。无异常后，执行 `import-output/01-import.sql`；唯一差别是最后 `COMMIT`。例如：`psql -v ON_ERROR_STOP=1 -f "schule2026-2027-1/import-output/01-import.sql"`。如有 SQL 错误，事务不会提交；退出当前失败事务并检查错误后再重试。不要复制粘贴部分 SQL 执行。
5. 执行只读 `import-output/02-verify.sql`。整份 CSV 预期至少 4,602 条本学期开课、6,979 条时段。核对 `pending` 列表、重叠时段及指定教学周查询。前端已有教师缓存最长可能在下次每小时校准时才更新，必要时按项目的缓存刷新流程处理。

脚本只补充新记录。相同学期、选课编号、原始行再次出现时跳过；同选课编号但内容改变时整个事务报错回滚，不覆盖已有课表。变更手工核实教师映射后，可改 `teacherOverrides` 并重新生成、重跑 SQL；已有非空的映射不允许悄悄改指另一个 ID。`setCurrentTerm=true` 会使本学期成为唯一的 `is_current` 学期，符合现有本学期筛选逻辑；若不想调整当前学期，请先在配置中改为 `false` 后重新生成。

课表只提供教学周编号，没有第一教学周日期及学校节次钟点。当前设计精确保存“第几周、星期几、第几节”，不虚构实际日期或时钟时间。后续如需要日历日期，可在拿到官方学期起始周后另建日期映射。

## 本地验证

`node scripts/timetable/verify-local.mjs` 在隔离的 PGlite PostgreSQL 中载入项目表结构和本地教师、课程目录，然后完整预演和两次导入，检查原始数据、6,979 条时段、教师页面去重、历史开课与评分不变，以及二次导入不增加记录。需要项目开发依赖（`npm ci`）。结果写入 `import-output/local-verification.json`。这不是线上导入，也不能代表线上数据库此刻的教师与课程目录。
