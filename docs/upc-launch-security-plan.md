## 1. 范围与固定产品决策

1. 仅服务中国石油大学（华东），在现有 React + Supabase 项目上增量开发，不重构整站。
2. 六维新评分保持 **4.0–5.0、最多一位小数**；保留历史记录及现有读取兼容，不转换历史分数。
3. 不开放文字评论，不恢复评论输入框；纠错、举报与撤回中的必要说明只进入私有审核队列。
4. 保留评价审核，公开评价统一匿名署名；账户关联仅供后台必要处理，不承诺无法追踪。
5. 不增加教师负面排行榜、全校最低分或倒数排名；保留当前按姓名和 ID 的稳定检索顺序。
6. 保留教师、课程、学期、开课关系及其来源；不覆盖现有官方 profile、`tt-` 课表身份和推断依据。
7. AI 问答、文字评论、教师排行榜、复杂积分、课程推荐算法、教务通知及其他无关功能均暂缓。
8. 密钥、学生邮箱、管理员账号、账户关联和原始审计明细不入 Git；仅提交脱敏结论和合成夹具。

新增编号使用 `SEC-*`。用户清单的 P0/P1/P2 表示本工作包的优先级，不替换旧计划的 P0–P4 阶段。

### SEC-01 · 运行态只读盘点

- [ ] 提供只读审计 SQL/脚本，按账户类型、邮箱域是否合规、确认状态、管理员绑定情况输出计数；
  另查普通评价重复组合、空/失效用户关联、历史文字、自定义署名和积分奖励可还原程度。
- [ ] 明细只保存在已忽略的 `temp/supabase-local/security-audit/`；Git 内仅记录计数、问题类型和方案，
  不保存原邮箱、账户 ID 或可还原身份的关联。既有非学生账户先出报告，不自动删除或批量改号。
- [ ] 记录本机数据基线及备份校验值，在独立隔离库恢复后验证迁移；原本机数据不作为破坏性测试夹具。
- [ ] 若有重复，给出逐组保留/归档映射及对点赞、积分、审核记录、统计的影响。无法确定主记录时，
  让唯一约束迁移明确报错并停止该步骤，不自动删行、合并评分、归零积分或伪造历史。

### SEC-P0-01 · 学生邮箱注册和完整准入边界

- [ ] 复用 `AuthModal` 和服务层，增加统一邮箱校验：先验证完整邮箱格式，再精确比较规范化后的域名
  `s.upc.edu.cn`。拒绝 QQ/163/Gmail 自助注册、`upc.edu.cn`、子域、伪装后缀、多 `@`、空邮箱；
  Gmail 仅精确地址私有邀请例外；前后端一致。
- [ ] 保留有效学校邮箱别名：不要求 local part 必须是数字，不提取学号，不擅自删除点号、加号后缀
  或合并邮箱。域名可不区分大小写；不能把字符串包含或宽泛后缀匹配当成域验证。
- [ ] 提供 Postgres `Before User Created Hook` 迁移，并在本机和目标项目**实际启用**。
  Hook 只授予 Auth 所需的最小执行权限，撤销 PUBLIC/anon/authenticated 执行；不使用可伪造的
  `user_metadata`、前端参数、Gmail 域名或自动白名单放行非学生注册。
- [ ] 保留邮件验证。评价 INSERT/UPDATE 和相关提交 RPC 从当前 `auth.users` 状态核验
  `auth.uid()`、学生域及 `email_confirmed_at`；不只信任前端、JWT 邮箱或“登录成功”。
  旧非学生账户可按受限流程查看本人资料、发起删除申请，但不得因此获得新评价资格。
- [ ] **单独封堵邮箱变更**：创建 Hook 不替代更新校验。在隔离 Auth 实测后提供最小服务端更新守卫，
  校验新邮箱请求及确认落地；覆盖直接 `auth.updateUser({ email })`、旧 token、重发、recovery、
  OTP/magic link、身份关联等实际开放路径。非学生域变更必须被拒绝，不能仅在换号后禁止打分。
- [ ] 盘点并关闭未使用的第三方、匿名、电话等注册/provider 路径；未来开放任何新路径前重新验证
  域和已确认邮箱，不能因页面没有入口就认定服务端不可调用。
- [ ] 管理员走独立受控建号/邀请及角色配置流程，先验证目标 Auth 对 Hook 的调用语义；
  不临时关闭全局 Hook、不提供公开管理员注册分支。管理资格与学生打分资格分开，
  使用 `docs/upc-auth-setup.md` 的 Gmail 私有邀请 + 稳定 `user_id` 授权步骤。

完成证据：使用公开 key 直接请求真实 Auth，学生域可注册但未确认不能评分；其他域创建失败；
直接变更邮箱和其他已开放路径不能绕过。保留合成别名用例，外部学校邮箱投递单独验收。

### SEC-P0-02 · 重复评价、限频、异常评分与积分

- [ ] 基于审计结果增加数据库组合唯一约束/唯一索引，键为用户×教师×课程×学期。
  未归档的 pending、approved、rejected 共用一个位置；驳回重提沿用原记录，不能只对 approved
  建唯一键。历史隔离记录如需新增归档字段，明确有效性条件，保留原行与引用，不自动清理。
- [ ] 保持现有修改规则：作者只能修改 pending/rejected，修改后进入 pending；已发布评价按撤回
  申请处理，不直接编辑为已通过。修改课程/学期也不能撞入其他已有组合。
- [ ] 在数据库事务中执行提交限频，使用服务端生成的时间和可防并发的锁/原子计数；禁止客户端
  伪造创建时刻绕过。前端防重复点击只改善体验；直接 INSERT、UPDATE、RPC 和可选缓存路径都受控。
  初始候选为每账户 60 秒 1 次、24 小时 10 次，做成受控配置并在隔离验证后确定，不硬编码在页面。
- [ ] 检测教师×课程×学期短时集中提交、异常账户和重复模式，写入私有风险原因并保持待审；
  已有集中异常需可在后台定位。不得仅凭相同评分自动判定恶意，也不得自动审核通过。
- [ ] 奖励去重改为持久业务键用户×教师×课程×学期，与评价 ID 去重共同生效；删除、撤回、归档、
  改课程后再提交、并发审核、驳回重审均不能重复获奖。奖励、积分流水和通过操作在同一事务完成。
- [ ] 回填可确认的历史奖励映射，不补发、不追溯扣分。已删评价导致关联无法还原的，列为待核验，
  为受影响范围设置奖励待核验状态，不将“找不到原关联”默认解释成从未奖励。

完成证据：顺序重复、不同新 ID、两条真实连接并发、修改组合冲突、跨账户/跨学期合法提交、
限频窗口和并发计数、删除后重提、并发审核、规则失败回滚均有断言。不能只用单连接 PGlite 模拟并发。

### SEC-P0-03 · 匿名公开、最小身份访问与删除申请

- [ ] `review_feed` 和所有公开 API 使用字段白名单：不返回用户 ID、邮箱、管理员/审核关联、
  风险标记、精确提交/审核时间；公开署名固定为“匿名石大学子”，移除公开昵称选项及身份复制分支。
  公众时间先按周展示，只返回粗化后的时间，不把原时间藏在 JSON 或排序字段里。
- [ ] 收紧新评价 comment 写入：数据库与服务端拒绝非空文字评论，公开投影不输出旧 comment。
  兼容列和历史数据可以保留；不得通过脚本清空历史文字，也不得恢复文字评论输入框。
- [ ] 普通审核员改读受控投影/RPC，不直接获得评价基表中的评价者关联；删除后台评价者邮箱显示
  和通用返回模型中的身份混用。作者仍可读取自己的必要账户关联，不能读其他人的。
- [ ] 敏感身份调查使用独立授权能力、必填用途和操作记录，不能凭普通审核角色任意查询。
  日志只保存必要主体、目标、操作、原因与时间，不复制邮箱/学号，不允许普通用户或审核员修改日志。
- [ ] 检查直连 REST、关联查询、可选 Node/Redis、浏览器缓存、Realtime 与日志路径；回收旧公开缓存，
  复核 publication/DELETE 事件和教师 `updated_at`，避免从旁路继续返回身份或精确事件时间。
- [ ] 修改桌面、移动、登录和评分说明：明确“对公众匿名；后台为认证、去重、审核、举报和撤回保留必要
  账户关联”，删除“绝对隐私”“完全无法追踪”等承诺；删除要求补充评语的旧审核话术。
- [ ] 在个人中心新增注销/个人数据删除申请，复用 SEC-P0-04 私有队列但校验本人身份。记录处理状态、

小样本阈值、按周时间和匿名署名只能降低识别风险，不应被包装成绝对隐私保证。

实施结束时必须交付：**修改文件清单、迁移 SQL 与执行顺序、自动化/真实环境测试结果、
未解决风险、需手动配置的 Supabase/域名/邮件事项**；每项标明本地、云端或生产状态。
只有满足完成标准的任务才能勾选，不以“写了迁移”替代“配置已生效并验证”。

## 8. Supabase 设计依据

2026-10-23 核对官方文档。实现时还需核对本机与目标项目实际支持版本。

- [Before User Created Hook](https://supabase.com/docs/guides/auth/auth-hooks/before-user-created-hook)：
  在创建用户之前判断是否允许注册。由此不能推断已有用户的邮箱更新已被覆盖。
- [Auth Hooks 安全模型](https://supabase.com/docs/guides/auth/auth-hooks)：Hook 执行权限应仅授予
  Auth 角色；本机配置与 SQL 函数必须一起验证。
- [updateUser](https://supabase.com/docs/reference/javascript/auth-updateuser)：登录用户存在直接修改
  邮箱的 Auth 接口，因此没有页面入口不能作为防绕过措施。
- [MFA](https://supabase.com/docs/guides/auth/auth-mfa)：强验证需要在授权边界检查 AAL，不能只实现
  绑定/验证码界面。
