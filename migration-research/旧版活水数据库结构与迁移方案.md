# 旧版交大活水：数据库结构调查与公开数据迁移方案

调查日期：2026-09-20。目标表以本次提供的 PostgreSQL / Supabase DDL 为准。现有权限：仅公开网站访问。

**建议：先保存公开课程与评价原始数据，再建立教师身份映射，最后导入新版。保留旧评分原貌，不把缺失信息补成默认高分。**

本次完成了公开源码调查、新版代码兼容检查及迁移方案设计；没有取得线上数据库备份，没有抓取全量教师/评价，没有连接或修改生产数据库。

## 1. 已确认的信息与证据边界

| 信息 | 结论及可信范围 |

| 当前应用响应 | 本次访问返回 Vercel Security Checkpoint；浏览器工具也因本地沙箱初始化故障无法启动，未取得业务页面或线上接口样本 |

## 2. 旧数据结构

### 2.1 LeanCloud / Ionic 版本：课程条目承载教师信息

关系：`教师身份（由课程信息识别） → 多条 Courses → 多条 Reviews`；`Reviews.authorId → 用户对象`。

这里 `Courses.objectId` 是课程条目 ID，不能直接当成全站唯一教师 ID。同名课程由不同教师教授，也不能只按课程名合并。

**Courses：客户端明确读取的字段**

| 字段 | 含义 |
|---|---|
| `objectId` | LeanCloud 课程条目 ID |
| `prof` | 教师姓名 |
| `name` | 课程名 |
| `position` | 职称 |
| `school`、`dept`、`campus` | 学校、院系、校区 |
| `rate1`、`rate2`、`rate3` | 专业水平、表达能力、亲和力的课程级聚合值 |
| `rateOverall` | 课程级综合平均分；云函数使用每条评价的 `rating.overall / 3` |
| `reviewCount`、`reviewGoodCount` | 课程级评价总量、好评数 |
| `attendanceOverall`、`attendanceCount` | 点名频率均值及有效填答数 |
| `homeworkOverall`、`homeworkCount` | 作业量均值及有效填答数 |
| `birdOverall`、`birdCount` | “水课程度”均值及有效填答数 |
| `examOverall`、`examCount` | 考试相关勾选项的聚合值及填答数 |
| `tags` | 云函数生成的是按标签 ID 索引的计数数组，并非标签名称字符串数组 |
| `createdAt`、`updatedAt` | 课程记录时间，不是教师入职时间或授课学期 |

**Reviews：客户端读取/写入以及云函数使用的字段**

| 字段 | 含义 |
|---|---|
| `objectId` | 评价 ID |
| `courseId` | 指向 `Courses` 的 Pointer |
| `authorId` | 指向用户对象的 Pointer；新旧账号不能直接对应 |
| `profName`、`courseName` | 冗余保存的教师名和课程名；与 Pointer 指向对象冲突时进入核对队列 |
| `comment` | 评价正文 |
| `rating.rate1`、`rating.rate2`、`rating.rate3` | 专业、表达、亲和力；UI 最大值为 5，实际零值/异常值仍需样本检查 |
| `rating.overall` | 三项之和，不能直接当作五分制分数 |
| `attendance`、`homework` | `{id,name,value}`；0=未填，1=无，2=少，3=中，4=多 |
| `bird` | 0=未填；1=绝非水课，2=正常水平，3=有点水分，4=水得不行 |
| `exam` | `touched`，以及 `examprep/openbook/oldquestion/easiness` 的勾选状态及 touched 标志 |
| `tags` | 评价选中的标签对象数组；需结合对应版本标签字典解释 ID |
| `upVote`、`downVote` | 赞与踩的计数 |
| `createdAt`、`updatedAt` | 原始记录时间；本次查到的提交逻辑没有授课学期字段 |

注意：Ionic 表单把 `exam.easiness` 标注为“给分”，但它是布尔勾选项，无法恢复新版 1–5 分的给分宽松度。2.0 模型中类似字段注释又是“题目容易”，所以必须按版本解释，不能通用映射。

### 2.2 PostgreSQL / 活水 2.0 公开后端：独立教师模型

| 表 / 模型 | 关键字段、关系 |
|---|---|
| `prof` / `Prof` | `name, code, gender, birth, hometown, motto, email, phone, officialSite, blog, exp, researchGroup, intro, education, research, achievement, scoreOverall`；关联 `school_id`、`position_id` |
| `school` | 学校实体 |
| `position` | 职称，`name` |
| `dept`、`prof_dept` | 院系及教师多院系关系；`dept` 包括 `shortname,longname,alias` |
| `course` | `name,isElective,audience,homepage,textbook,credit`，多种聚合分；`prof_id`、`school_id`，另有院系关联 |
| `review` | `text,professional,expressive,kind,rateHomework,rateAttend,rateBirdy,rateExam,hasExam,examprep,openbook,oldquestion,easymark,upVote,downVote,created_at,updated_at`；关联教师、课程、作者 |
| `prof_stat`、`course_stat` | 聚合评分、评价数、各维度有效样本数、标签与考试项计数等 |
| `tag` 及关联表 | 教师、课程、评价标签 |
| `comment` | 对评价等对象的评论，可通过 `parent_id` 形成回复关系；不能当成新的教师评价重复计数 |
| 用户及赞踩关联表 | 账号和互动关系；不属于此次公开教师数据迁移范围 |

2.0 评分模型的数值约束包含 0–5，和 Ionic 可选字段的 0–4 编码不同。是否把 0 当作有效评分，必须结合该版本客户端/接口样本判断。

## 3. 面向新版的字段映射

### 3.1 teachers

| 新字段 | 迁移规则 |
|---|---|
| `id` | 有稳定旧教师 ID 时用带来源命名空间的确定性 ID；只有 Courses 时为确认后的教师簇分配持久 ID，并保存每个旧 course ID → 新 teacher ID 的映射 |
| `name` | Ionic `prof`；2.0 `Prof.name`。规范化空格，不擅自改姓名、合并异体字 |
| `title` | `position` 或 `Position.name`；缺失填“职称未知”，不能默认“讲师” |
| `college` | `dept` / `Depts` 规范化。学院旧名保留为别名，多院系不能无依据任取一个 |
| `campus` | 有证据时统一校区名称；缺失为“校区未知”。历史校区不能证明当前校区 |
| `courses` | 同一教师全部课程名去重后的 JSON 字符串数组；课程 ID、原始属性保存在独立映射/归档中 |
| `is_teaching_this_term` | 历史库无法确认。推荐允许 NULL 表示未知，仅有当前教务数据时填 true/false |
| `has_historical_data` | 实际有旧来源记录则为 true；来源属性与年份无关，不能只认“2024 年以前” |
| `tags` | 解码、去重后的标签名称数组；旧课程标签计数数组不得原样写入 |
| `review_count` | 新站实际已导入且 approved 的评价数。旧站展示总数另存，不能冒充已迁入条数 |
| 六维评分、`overall_score` | 按下节规则处理，缺失保留 NULL；旧综合分单独保存并标明口径 |
| `created_at` | 定义为新教师实体建档时间；原始课程/教师时间另存于来源归档 |

教师去重优先级：稳定教师 ID / 学校教师编号 > 经核实的学校＋学院＋姓名及辅助证据。学校＋学院＋姓名只能产生候选簇，同院同名仍需核对；跨学院、跨校区不能直接合并，也不能仅因校区不同强制拆分。

有歧义的记录保留独立待核身份，不强行挂到已有教师。新旧教师匹配表要同时记录依据、审核状态、涉及的旧课程 ID。已确认映射后固定新 ID，后续改院名不能引起 ID 漂移。

### 3.2 reviews

| 新字段 | 迁移规则 |
|---|---|
| `id` | 如 `legacy:leancloud:review:<objectId>`，或 `legacy:pg2:review:<id>`；跨来源不冲突，重复运行不重复插入 |
| `teacher_id` | Ionic 必须通过旧 `courseId` → 新教师映射；2.0 按旧 `prof_id`。关联缺失的记录进入隔离区 |
| `course_name` | 指向课程的名称，并保存评价里的历史名称；冲突需解释，不静默覆盖 |
| `year_term` | 原数据没有则填“历史学期未知”；不能根据发帖日期或作者入学年份推断 |
| `comment` | 保留原文和换行；展示时按文本渲染或清洗不安全 HTML，原文单独归档 |
| `author_nickname` | 保留公开展示昵称；没有则“旧版匿名用户”。不得因作者 Pointer 无法读取而丢弃评价 |
| `user_id`、`user_email` | NULL。不爬取用户表，不导入旧密码、令牌、非公开邮箱，不凭昵称绑定新版账号 |
| `is_historical_migrated` | true |
| `status` | 明确写入 pending，核验和审核后 approved；只对确认符合新站发布标准的批次采用批量批准 |
| `likes` | 合法非负整数 `upVote`；缺失可用 0 并记录“未知”。`downVote` 单独归档，不相减冒充点赞 |
| `created_at` | 原始评价时间，准确转换到 timestamptz；有时区偏移的按偏移解析，无时区需先确认来源时区 |

原始评价时间缺失时，应允许 NULL 并增加 `imported_at`，或先隔离；不要用现在时间伪装历史发帖时间。缺课程名同理，确认不了则标记未知或隔离。

`user_profiles`、`point_transactions`、`admin_users` 不随本次公开教师迁移导入。历史评价审核不能触发新用户积分奖励。

### 3.3 评分：第一阶段保留旧体系，第二阶段再决定换算

**推荐第一阶段：六维评分只展示新站真实填答结果，旧记录单独显示旧版指标。** 这样仍能迁入教师、课程、正文、时间、赞数和历史评分，不必为了适应表结构生成新评分。

| 旧指标 | 新字段 | 判断 |
|---|---|---|
| `rating.rate3` / `kind`：亲和力或友好 | `approachability` | 最接近；确认量表和零值规则后可直接对应，但仍保留来源 |
| `attendance.value`：点名频率 1–4 | `attendance_strictness` | 可选近似换算 `1 + (x-1)*4/3`，即 1、2.33、3.67、5；0→NULL。频率与严格度并非完全等价，第一阶段建议留在旧指标 |
| `homework.value`：作业量 | `workload_difficulty` | 只反映数量，不能证明难度；默认不自动写入 |
| 专业水平、表达能力 | `teaching_quality` | 不是同一问题。若采用二者均值，只能标为“历史估算”，不得称为原始教学质量分 |
| `exam` 勾选项、`bird` 水课程度 | `grading_leniency` | 无法恢复 1–5 的给分宽松度，留 NULL |
| 无直接字段 | `effort_matters` | 留 NULL，不能从“水课程度”或正文自动推导真实评分 |
| `rating.overall` | 旧综合分 | Ionic 是三项总和；先验证总和一致，再除以 3。Courses.rateOverall 已经归一化，不要重复除以 3 |

不要简单平均各门课程的均分。能取得评价明细时按去重后的评价重新聚合；只能取得均值时，每个维度必须使用自己的有效填答数加权：`SUM(mean_d * count_d) / SUM(count_d)`。不得把旧聚合快照与其对应评价明细再相加。

旧云函数 `updateSingleCourseStat` 的评价查询未显式设置分页，且零评价时直接返回；因此源码存在统计不完整或陈旧的可能，旧聚合数只能用于对账，不能当作完整性证明。

## 4. 新库与前端的最小必要调整

建议不大改现有五张业务表，新增以下迁移配套结构；以下是设计要求，不是已运行的 DDL。

| 配套结构 | 用途及关键约束 |
|---|---|
| 私有 `migration_batches` | 批次 ID、来源、采集时间范围、规则版本、输入校验和、计数、状态 |
| 私有 `source_records` | `source_system, entity_type, source_id, fetched_at, source_updated_at, source_url, payload, payload_hash, batch_id`；原始快照可追加保存，唯一键包含快照/批次身份 |
| 私有 `teacher_identity_map` | 每个来源教师/课程 ID 映射到新教师，记录判断依据和确认状态；来源实体标识唯一 |
| 私有 `migration_changes` | 每批插入/更新的目标 ID、变更前后值或摘要，用于精确回滚及冲突检测 |
| 公开但脱敏的历史指标投影 | 按教师/评价显示专业、表达、亲和力、点名、作业量、考试原选项、旧综合分；不得直接暴露原始 payload |

业务表可增加 `source_system/source_id/import_batch_id/imported_at` 等来源字段，或通过来源关联表实现；无论方案如何，都要保留稳定来源唯一约束。单一 `is_historical_migrated` 不足以去重或定位回滚批次。

需要同步调整：

1. `teachers` 的七个评分列允许 NULL，移除 3/4/4.5 等默认分；无真实评分显示“暂无评分”。`is_teaching_this_term` 允许 NULL 或另加明确的授课状态。
2. 前端类型支持未知评分、未知校区、授课状态未知。当前 `src/types.ts` 将评分设为必填 number，校区仅有犀浦/九里两种，无法忠实承载所有旧记录。
3. `src/services/supabaseService.ts` 的 `Number(row.overall_score) || 4.5` 和六维类似写法会把 NULL/0 改成默认分，必须替换。不要只改 SQL 而保留这些兜底。
4. 详情页、排序、雷达图、推荐算法、AI 引用都要处理 NULL；不能让 `null <= 2.2` 等 JS 隐式转换把无数据教师推成“不点名”。无当前授课证据的历史教师不进入本学期开课候选池。
5. 原生六维分与历史旧分分栏，记录样本数。新版综合分公式需单独定义，不能把严格度、作业难度等方向不同的量简单等权平均。
6. 评价审核、删除、转移教师关联后，由服务端触发器或统一事务重算 approved 数量及有效评分。当前 `src/App.tsx` 审核函数可见的是前端 `reviewCount + 1`，不能承担迁移对账。

部署前还应核对实际 Supabase 配置。本地 `supabase_schema.sql` 与用户给出的 DDL 有差异（如 `rejection_reason`、ON DELETE CASCADE），且本地文件含公开更新/删除评价、公开管理管理员的宽松策略。若生产使用相同策略，迁入 pending 记录也可能被公开读取或更改：必须采用数据库级 approved 公共读取与服务端授权写入。该问题来自实际仓库文件，生产策略是否相同尚未验证。

私有归档不加入 Supabase exposed schemas，不授予 anon/authenticated 原始记录读取权限；涉及原作者标识等信息，仅服务端迁移使用。迁移密钥不得进入 Vite 前端环境变量。

## 5. 仅有公开访问权限时的执行路线

### 阶段 A：先恢复正常公开读取，确认源版本

- 用正常浏览器打开应用，取 3–5 条课程与评价的脱敏样本，确认 Courses/Reviews Pointer 结构或 2.0 的 prof/course/review 结构。
- 仅使用普通访问者本来能读取的页面/接口；若仍被安全验证阻断，则请求站方提供公开字段 JSON/CSV，不能据公开源码中的密钥调用管理接口或云函数。
- 若你自己的浏览器此前加载过 Ionic 版，可检查该站点 localStorage 中是否仍有课程缓存；源码将课程数据缓存在客户端。它只能作为带时间标记的课程补充快照，不是完整评价备份，也不能保证为当前数据。
- 第三方镜像最多作为补充线索：必须确认来源、时间、字段和重复关系，不能直接当成官方全量库。公开仓库本身也不等于可恢复数据备份。

**本次真正的启动条件：拿到一个正常返回业务数据的公开读取通道，或公开字段导出文件。当前安全验证页不能提供这些数据。**

### 阶段 B：保存原始记录和采集清单

- 先课程/教师列表，后按 course ID 逐门采集评价。覆盖分页，不能只采“热门”“最新”第一页。
- 初始单并发、约 1 请求/秒作为建议值，尊重实际站点限制；429 遵循 Retry-After，连续错误暂停并记录。
- 优先稳定排序和服务端支持的游标；如仅支持 offset，用稳定排序、重叠页去重、末次复扫。没有实际接口前不预设可用参数或可用 limit。
- 保存原始 ID、关联 ID、响应或最小必需字段、抓取时间、来源 URL、内容校验和；不保存登录令牌或不必要的个人资料。
- 分别记录“列表枚举完成”“该课程评价分页完成”“来源展示评价数”“实际读到条数”“失败页”。页面总数可能包含不可见记录，不相等时报告差值。
- 没有可枚举列表时，用学院分类和搜索补充仍只能称“已发现公开记录”，不能宣称全站完整。

### 阶段 C：规范化、身份消歧及试迁

- 建立学院/校区/职称别名字典；仅确定等价关系才归一化，保留原值。
- 先确定教师映射，再把课程及评价挂到教师；多教师共授而目标表仅支持单教师时进入人工处理，不能复制一条评价到多人后重复计数。
- 旧 ID 去重优先；没有 ID 时使用来源 URL 和稳定记录指纹作为辅助，不能仅按相同正文删除评价。
- 把缺失关联、非法评分、异常日期、同名冲突、内容异常放到隔离清单，保留原因和源 ID。
- 在测试库先选约 20–50 名教师，覆盖多课程、同名、多院系、无评分、无作者、长文、不同校区、历史日期。
- 验证字段、UI 与推荐兼容后，再执行全量批次。导入优先暂存表 COPY 加事务写入，不能借用“用户提交评价”入口。

### 阶段 D：全量导入、对账、发布

导入顺序：批次/原始记录 → 教师身份映射 → teachers → 来源课程映射及历史指标 → reviews → 审核后的统计重算。

同源主键冲突时核对映射和内容哈希：相同则跳过；来源变化进入受控更新。不得无条件 upsert 覆盖新站已有教师资料、审核结论、新点赞和新评价。

| 验收项目 | 可核对标准 |
|---|---|
| 记录守恒 | 原始唯一评价数 = 本批新增 + 已存在去重 + 隔离 + 明确排除；分类互斥并保留源 ID |
| 关联 | 已发布评价无孤儿 teacher_id，旧课程到教师的映射可追溯；同名冲突未被静默合并 |
| 计数 | teachers.review_count 与该教师所有 approved 评价数量一致；pending 不计入 |
| 分数 | 未填为 NULL，不出现默认制造的评分；每维分别计算有效样本数；旧/新口径可区分 |
| 日期与文本 | 没有乱码、截断、二次 HTML 实体转义；发帖时间未变成导入时间，学期未知明确显示 |
| 幂等 | 同一批次重跑不新增重复教师或评价，不重复发积分，不覆盖新站互动 |
| 权限 | 普通访问者只读可发布内容，不能读原始归档、改审核状态或授予管理员身份 |
| 界面 | 缺失分数不会显示为 0/4.5、生成推荐标签、进入错误排行；历史课程不会自动显示为本学期开课 |

只有公开权限时无法冻结旧站。正式发布前补扫新增与已知记录更新，保存采集截止时间；公开列表一次缺席不能证明被删除。新站可以继续使用，公开数据的覆盖范围和采集窗口要在迁移记录中保留。

### 阶段 E：回滚

- 导入前备份目标库，记录变更前的教师字段及关联；先在测试库演练恢复。
- 尚未发布时可按批次撤销新增评价，再撤销无任何评价/业务引用的新增教师，重新计算计数。
- 已发布后优先隐藏有问题批次并按变更日志修复；对发布后被用户修改的记录做冲突检测，不直接恢复旧快照覆盖用户新操作。
- 不能运行“删除所有 historical=true”，不能直接删除教师触发级联丢失新评价，也不能回滚其他历史批次。
